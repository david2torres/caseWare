## How to run

- Java (Part 2): `cd server && mvn test` — Java 21, JUnit 5, no other dependencies.
- Angular (Part 3): `cd client && npm install && npm test -- --watch=false`, and `npm start` to click through the fixture
  scenarios (Angular 21, standalone components, signals, zoneless, Vitest).

## Assumptions

- The engagement template **index** can be populated by hooks on engagement creation and decision completion, plus a
  one-off backfill for existing engagements (the only place we pay the 1-minute load).
- Applying always targets the **latest** version; intermediate versions are not individually selectable.
- The diff tool can diff **any** two versions of a template (not only consecutive ones), as the brief states. The net
  summary is taken from `diff(baseline, latest)`; consecutive diffs are used only for "changed in vN" attribution.
- Declining records `declinedThroughVersion`; the engagement's content baseline does not move. Part 2 assumes no decision
  history, as instructed, so the Java evaluator uses the recorded version as the baseline.
- A decision is only allowed once the summary is `READY` (users should not decide blind).
- Section display names come from template content (`sections.*.displayName`, seen in the AUDIT-CA v5 fragment);
  where unknown, keys are humanised (`riskAssessment` → "Risk assessment").
- Sample data edits, made to exercise states the brief asks about:
  - AUDIT-CA v3 → v5 net diff is not in the pack; derived from v3→v4 + v4→v5.
  - Client fixture: ENG-1010 summary starts `COMPUTING` (ready on the next poll), ENG-1011 is `UNAVAILABLE`,
    ENG-1012 is `NOT_YET_INDEXED`.
- The client fixture's `ChangeItem`s were generated by running the Java summary code over the sample diffs, so the three
  layers (contract, Java, Angular) agree on real output rather than on hand-written examples.
- Out of scope: persistence, HTTP layer, auth, French localisation, pagination of very large summaries.

## AI usage

**Tools used:** [Claude.ai"].

**Where AI helped:**

- Initial draft of the Java domain model and tests.
- Initial structure (_scaffolding_) of Angular components.
- Conversion of the design into a compact contract.
- Generation of test data (_fixtures_) for the client based on the Java code.
- Evaluating future steps and necessary adjustments.
- Updating the High-Level Architecture document based on requirements and implemented developments.

**Where I corrected, rewrote or ignored AI output:**

- Adjustments to the frontend architecture definition and visual component development.
- Separation of concerns by implementing SOLID and Clean Code principles.
- Implementation of a new architecture (Clean Architecture) to facilitate maintenance and scalability.

**How I would guide other engineers using AI on this system:**

- Give the model the contract and the domain invariants (never guess a version; UNKNOWN is a valid answer; apply targets
  latest) and ask it to write tests first against the sample diffs.
- Treat generated code as a draft: review against the contract, run the tests, and read every user-facing string.
- Keep AI out of the request path for anything that decides state; use it at authoring time (drafts, test cases, review).
- Require golden tests for any new wording rule, whether written by a person or a model.

**Where AI should not be trusted in this domain:**

- Deciding or explaining the _professional relevance_ of a change (e.g., whether a lower materiality threshold affects the
  conclusions of an engagement).
- Generating real-time summaries on demand without review: non-deterministic text breaks the audit trail of "what the user
  saw when they applied the change." - Tenant isolation/security code (strict isolation between instances sharing a template database) without thorough human review.

## What I would do next

1. *Contract-first* approach: OpenAPI file to generate Java DTOs, with CI validation.
2. Real `HttpClient` gateway and list polling based on ETags; move polling to a schedule that detects the `visibilitychange` event.
3. Decision history in the evaluator (`declinedThroughVersion`, highlighting elements subsequent to the last rejection).
4. Wording rules managed by the content team (display names for fields like `tolerance`, units like "%") and French language support.
5. Implementation of accessibility and internationalization (i18n) for centralized text management.
6. Expand the use of constants in the frontend to avoid handling static variables in logic files, thereby reducing the margin for error.
7. Capture the summary hash alongside each decision to ensure traceability (audit trail).
